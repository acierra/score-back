В существующем проекте обнаружены два отдельных пути реконструкции:

1. `CloudPointClient`: получает изображения от Unity по JSON-RPC,
   переводит их в серый формат, ректифицирует, вычисляет disparity,

оставило бы экспериментальную программу без новой предобработки.
Поэтому общий модуль подключён в обоих местах.

## Почему выбран такой дизайн

`IStereoPreprocessor` задаёт обработку сразу двух изображений. Это
позволяет явно использовать статистики пары или опорной камеры.
При интерфейсе для одиночного изображения согласованную обработку
двух камер было бы сложнее контролировать.

`StereoPreprocessorChain` содержит упорядоченный список обработчиков.
Результат каждого шага становится входом следующего. Это подходящая
для задачи форма цепочки обработчиков: выполняются все выбранные
алгоритмы, а не только первый подходящий обработчик. Порядок хранится
в YAML и воспроизводится при каждом запуске.

Интерфейс принимает `CV_8UC1`, потому что оба существующих пути уже
переводят изображения в серый формат до ректификации. Сохранение этого
порядка уменьшает объём вмешательства в рабочий pipeline. Например,
текущий CLAHE применяется к серому изображению; вариант с обработкой
яркостного канала цветной модели пока не реализован.

## Что реализовано

| Метод | Что делает и зачем нужен |
|---|---|
| `none` | Возвращает исходную пару без копирования пикселей; контрольный вариант |
| `pair_normalize` | Приводит яркость и контраст правого изображения к левому; направлен на межкамерные фотометрические различия |
| `clahe` | Усиливает локальный контраст с ограничением усиления; экспериментальный кандидат для слабой текстуры |
| `local_normalize` | Нормализует локальные среднее и отклонение с общим целевым уровнем пары; базовый вариант типа Wallis |
| `illumination_correction` | Делит яркость на локальную оценку освещения; простой кандидат для неравномерной освещённости |
| `edge_preserving_denoise` | Bilateral-фильтрация с фиксированными одинаковыми параметрами обеих камер |
| `specular_mask` | Маски ярких ненадёжных областей в обеих камерах; исключение соответствий перед построением облака |

Независимая адаптация камер для CLAHE и локальных методов требует
явного `statistics: independent`. Нормализация по левому изображению
требует `statistics: left_reference`. Благодаря этому различие между
парной и независимой обработкой видно в конфигурации эксперимента.

Локальная нормализация не названа полной реализацией параметрического
Wallis, а коррекция освещения — Retinex: их текущие формулы проще.
Для почти постоянных изображений предусмотрена защита от деления
на ноль. Результат ограничен диапазоном 0–255.

Маска бликов не закрашивает изображение и не создаёт синтетическую
текстуру. После matching исключается точка, если закрыт левый пиксель
или соответствующий правый пиксель в координате `x-d`. Маски сохраняются
при последующих шагах цепочки. Детектор использует фиксированный порог
яркости и расширение маски; работа с цветовой насыщенностью потребовала
бы изменения серого входного контракта. Поэтому это базовый детектор
кандидатов в блики, который также может исключить яркую ткань.
Его эффект нужно оценивать вместе с потерей покрытия.

## Конфигурация и совместимость

Добавлена секция `cloud_point.preprocessing` с полями `enabled` и `chain`.
Отсутствующая секция, пустая цепочка, шаг `none` или `enabled: false`
дают режим без обработки. Старые YAML-файлы продолжают работать.
У клиента новый параметр конструктора имеет значение по умолчанию,
поэтому прежние вызовы C++ не требуют изменения исходного кода.
После изменения библиотеки нужна пересборка клиента: двоичная
совместимость прежнего символа конструктора не сохраняется.

Парсер отклоняет неизвестные методы, опечатки в ключах, неверный тип
цепочки и недопустимые числовые параметры. Настройки проверяются
даже у отключённой цепочки, чтобы ошибка не проявлялась спустя время
при её включении. Переключение выполняется конфигурацией при создании
клиента; горячая перезагрузка YAML во время работы не добавлялась.

Калибровка, карты ректификации, Q, алгоритмы CPU/GPU, параметры matcher,
фильтры облака и форматы экспорта сохранены. Цветное изображение viewer
остаётся исходным ректифицированным изображением, поэтому изменение
контраста для matching не меняет цветовую визуализацию облака.
Проверяется сохранение размера и типа изображений после каждого шага.
Для конкурентных pipeline нужен отдельный экземпляр цепочки.

## Сравнение с baseline

В benchmark добавлены загрузка той же секции YAML, `preprocessing_ms`,
полные настройки цепочки в JSON и необязательное сохранение изображений
до и после обработки. Время matcher измеряется отдельно от предобработки.
Сохраняемая disparity соответствует выходу matcher: при включённых
WLS/median она включает эти фильтры. Для исходной disparity их нужно
отключить; это прямо указано в инструкции.

`scripts/compare_preprocessing.py` запускает baseline `none` и заданные
варианты на одинаковых кадрах. По умолчанию фиксируются CPU StereoSGBM,
160 уровней диспаритета и глубина 0.02–0.30 м. Настройки реконструкции
проверяются на совпадение. YAML каждого варианта меняет только
предобработку; другие поля файла не заменяют общие настройки benchmark.

JSON и CSV содержат метрики и их разность с baseline по каждому кадру,
команды запуска, параметры и контрольные суммы. Отсутствие эталона,
ошибка запуска и отсутствие оцениваемых точек считаются ошибками,
а не нулевой ошибкой реконструкции. Автоматический выбор «лучшего»
метода и проверка статистической значимости не добавлялись.

## Данные для количественного сравнения

Источник данных — [maxhallan7/scared на Hugging Face](https://huggingface.co/datasets/maxhallan7/scared),
указанный в README самого score-back. Зафиксирована версия
`c1246e4f9f52e1ffd51fa45f8544288771785189`.
Из dataset_1, dataset_2 и dataset_3 взяты keyframe_1 и keyframe_2.
Для каждого кадра загружены только `Left_Image.png`, `Right_Image.png`,
`endoscope_calibration.yaml` и `point_cloud.obj`: всего 24 файла.
HTTP Range позволил получить нужные файлы без загрузки полных архивов
с видео; передано около 408 МБ. Для каждого файла сохранены исходный
путь в ZIP, CRC32 и SHA-256 в `reports/task12/data-provenance.json`.

Облако эталона хранится в миллиметрах; существующий загрузчик переводит
его в метры, сохраняет пиксельный порядок и NaN и ректифицирует в систему
левой камеры. Сравнение выполняется без ICP. В отчёте используются
пиксельно согласованные метрики до PLY-прореживания и триангуляции.

Общие настройки: CPU StereoSGBM, min disparity 0, 160 уровней,
блок 5, P1=200 и P2=800, uniqueness 10, speckle window 100/range 2,
LRC 1, pre-filter cap 31, median 0, WLS выключен, offset 0,
фильтр выбросов выключен, диапазон глубины 0.02–0.30 м.
Меняется только предобработка. Восьмой вариант — цепочка bilateral→CLAHE
с теми же параметрами, что у отдельных методов. Объём сравнения —
48 запусков (6 кадров × 8 вариантов), все успешны.

Ошибки сравниваются совместно с покрытием: метод может снизить ошибку
лишь за счёт исключения сложных точек. Средние по таблице рассчитываются
по кадрам с равными весами. Выводы относятся к этим шести кадрам; перенос на другие
эндоскопические сцены требует отдельной проверки. Время измеряется в виртуальной машине
по одному запуску на вариант и кадр; его следует считать ориентировочным.

Выводы по остальным вариантам:

- `pair_normalize`: MAE улучшилась на двух из шести кадров, средняя ошибка
  выросла примерно на 4.88%. Коррекция межкамерной фотометрии с этими
  параметрами не стала устойчивым улучшением.
- `clahe`: MAE не улучшилась ни на одном кадре; средняя MAE выросла на
  23.03%, RMSE — примерно на 86.46%, покрытие снизилось на 4.80 п.п.
  Усиление контраста само по себе здесь не дало лучшей реконструкции.
- `local_normalize`: средняя MAE выросла на 3.95%, покрытие потеряло
  12.08 п.п. Для этой реализации и параметров результат хуже baseline.
- `illumination_correction`: улучшение MAE на трёх кадрах из шести,
  но средняя ошибка практически не снизилась, а RMSE и потери покрытия
  выросли. Эффект неоднороден между сценами.
- `specular_mask`: маска действительно исключала соответствия — в среднем
  около 16.8 тысячи на кадр. Покрытие снизилось на 1.37 п.п., средняя MAE
  слегка выросла (около 0.28%). Значит, фиксированный яркостный порог
  в этой выборке не выделил преимущественно ошибочные соответствия.
- Цепочка bilateral→CLAHE не улучшила MAE ни на одном кадре; её средняя
  ошибка выше baseline. Добавление полезного отдельно шага к другому
  методу не гарантирует полезность их композиции.

Практическое решение: оставить `none` значением по умолчанию для
совместимости, а `edge_preserving_denoise` рекомендовать как первый
экспериментальный вариант для этой конфигурации. Автоматическое включение
методов для всех сцен или перенос в видеобэкенд da Vinci этой работой
не выполняется. Выбор для другой камеры и освещения требует отдельного
сравнения; результаты шести кадров не являются доказательством общего
превосходства метода.

Полные данные сохранены в `reports/task12/comparison.csv` (48 строк
по отдельным кадрам) и `comparison.json` (метрики, настройки, команды,
хэши конфигураций и benchmark). Общая сводка — `summary.csv` и
`summary.json`; конфигурация цепочки — `denoise_clahe.yml`.

## Влияние на общий проект

Главное изменение — экспериментальный выбор предобработки стал
отдельной настройкой, общей для Unity-клиента и оценки на SCARED.
Новый алгоритм больше не требует переписывать геометрическую часть
реконструкции. При отключённой обработке сохраняется прежний результат;
при включённой меняются значения пикселей, а через них могут измениться
disparity, плотность облака и геометрическая ошибка.

Усиление контраста может помочь слабой текстуре, но также усилить шум
или нарушить сходство камер. Фильтрация шума может сгладить полезные
детали. Поэтому реализованные методы остаются экспериментальными,
а включение цепочки не означает автоматического улучшения качества.
Каждый активный шаг добавляет вычислительную работу; её время теперь
измеряется отдельно. Обещания работы в реальном времени не делаются.

## Дальнейшие этапы

Окончательное сравнение использует заранее выбранные шесть кадров и
фиксированные параметры методов, без подбора по измеряемым ошибкам.
Расширение числа сцен и подбор параметров на отдельном наборе настройки
позволят проверить переносимость выводов, но выходят за рамки первого
контролируемого сравнения.

Маскирование бликов входит в реализованный обязательный набор.
SERV-CT, Retinex, восстановление
бликов, региональные метрики, GPU-эксперименты и другие расширения
не включены. Дополнительные возможности сверх согласованной задачи
потребуют отдельного обсуждения.

Порядок запуска и примеры конфигурации находятся в
[инструкции](preprocessing.md). Основной проект сохраняется в
`Documents/itmo/диплом/score-back`; копия в рабочей папке Codex
использовалась для подготовки изменений. Коммиты в исходном проекте
и отправка изменений на сервер не выполнялись.
